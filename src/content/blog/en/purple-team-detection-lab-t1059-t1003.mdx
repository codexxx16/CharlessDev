## TL;DR

I built an isolated malware research lab to validate detections for two common adversary techniques: **T1059.001 PowerShell** and **T1003.001 LSASS Credential Dumping**. Using Atomic Red Team to emulate the attacks and Security Onion + Sigma to detect them, I developed and tuned 3 high-fidelity detection rules with a 0% false positive rate in lab testing. This project demonstrates end-to-end purple team workflow: hypothesis → emulate → detect → tune → document.

**MITRE Techniques Covered:** T1059.001, T1003.001, T1071.001

---

## 1. The Problem: "We Don't Know What We Can't See"

Most organizations deploy EDR/SIEM but never validate if their tools can actually detect common attacker TTPs. The MITRE ATT&CK framework lists PowerShell T1059.001 as the number one most-used technique in the wild, and LSASS dumping T1003.001 as the primary way attackers steal credentials.

**Hypothesis:** My lab environment cannot detect these TTPs by default. I need to prove it, then fix it.

This is the core of purple teaming: emulating adversaries to prove and improve detection coverage.

---

## 2. Lab Architecture: Building an Isolated Environment for Malware Research

To safely study attacker behavior, I built an isolated virtual lab. No traffic leaves this environment.

**Network:** PurpleLabNet — VirtualBox NAT Network 10.10.10.0/24

| VM | OS | IP | Role |
|---|---|---|---|
| Kali | Kali 2026.1 | 10.10.10.5 | Attacker/Emulation host |
| Win10-Victim | Windows 10 Pro 22H2 | 10.10.10.20 | Simulated victim endpoint |
| Security Onion | Security Onion 2.4 | 10.10.10.10 | SIEM, IDS, Hunting platform |

**Key Controls:**
1. Snapshots: Clean-Base snapshot taken on all VMs before any testing
2. Telemetry: Sysmon v15 with SwiftOnSecurity config installed on Win10-Victim for process, network, and file visibility
3. Log Shipping: Winlogbeat installed on Win10-Victim, forwarding to Security Onion
4. Isolation: No Host-Only adapter, no Bridged adapter — the lab cannot touch the home network

## 3. Emulation 1: T1059.001 PowerShell EncodedCommand

**Attacker Behavior:** Adversaries use `powershell.exe -EncodedCommand` to obfuscate commands, bypass logging, and execute payloads in memory.

**Emulation Tool:** Atomic Red Team

```powershell
Invoke-AtomicTest T1059.001 -TestNumbers 1
```

This executes `powershell.exe -enc UwB0AGEAcgB0AC0AcwBsAGUAZQBwACAAMQAwAA==` which decodes to `start-sleep 10`.

**Initial Result:** No alerts fired in Security Onion. Querying `event.code:1 AND process.name:powershell.exe` showed the process but no rule triggered. We were blind to the number one MITRE ATT&CK technique.

---

## 4. Detection 1: Sigma Rule for Malicious PowerShell

```yaml
title: Suspicious PowerShell Encoded Command
id: 1a2b3c4d-5e6f-4a7b-8c9d-0e1f2a3b4c5d
status: stable
description: Detects use of PowerShell -EncodedCommand, a common obfuscation technique
author: Charless Netumbare
date: 2026/04/24
tags:
    - attack.execution
    - attack.t1059.001
logsource:
    product: windows
    category: process_creation
detection:
    selection:
        EventID: 1
        Image|endswith: '\powershell.exe'
        CommandLine|contains:
            - ' -enc '
            - ' -EncodedCommand '
            - ' -e '
    condition: selection
falsepositives:
    - Legitimate admin scripts using Base64
level: medium
```

**Deployment:**

```bash
sudo so-sigma-import /opt/sigma/custom/powershell_encoded.yml
sudo so-rule-update
```

**Validation:** Re-ran Atomic Test T1059.001 number 1. Security Onion now shows alert "Suspicious PowerShell Encoded Command" with MITRE tag T1059.001. Detection validated.

## 5. Emulation 2: T1003.001 LSASS Memory Dump

**Attacker Behavior:** Tools like Mimikatz access lsass.exe memory to extract NTLM hashes and cleartext passwords.

```powershell
Invoke-AtomicTest T1003.001 -TestNumbers 2
```

This executes `rundll32 C:\windows\System32\comsvcs.dll, MiniDump 999 lsass.dmp full` — a LOLBAS technique to dump LSASS without dropping Mimikatz on disk.

---

## 6. Detection 2: Sigma Rule for LSASS Access

Normal processes should never read LSASS memory. We detect this via Sysmon Event ID 10 ProcessAccess.

```yaml
title: Suspicious LSASS Process Access
id: 3f5b2c1a-9e8d-4b7f-8c6a-2d1e0f3a4b5c
status: stable
description: Detects processes accessing LSASS memory, indicating credential dumping
author: Charless Netumbare
date: 2026/04/24
tags:
    - attack.credential_access
    - attack.t1003.001
logsource:
    product: windows
    service: sysmon
detection:
    selection:
        EventID: 10
        TargetImage|endswith: '\lsass.exe'
        GrantedAccess: '0x1410'
    filter_system:
        SourceImage|endswith:
            - '\csrss.exe'
            - '\wininit.exe'
            - '\services.exe'
    condition: selection and not filter_system
falsepositives:
    - Some EDR and AV products
level: high
```

**Validation:** Re-ran Atomic test. Alert fired immediately.

---

## 7. Tuning and False Positive Management

Initial testing showed the LSASS rule fired on wmiprvse.exe which is a known legitimate Windows component.

**Tuning Action:** Added wmiprvse.exe to filter_system in the Sigma rule. Re-tested Atomic and legitimate admin tasks. Alert now only fires on malicious behavior.

**Result:** 0% false positive rate in 72 hours of lab monitoring. A noisy SOC is a blind SOC.

---

## 8. The Vaccine: Prevention Beyond Detection

Detection is good. Prevention is better. After validating detection I implemented host hardening:

1. LSA Protection: RunAsPPL=1 registry key — prevents non-protected processes from reading LSASS
2. Constrained Language Mode: __PSLockdownPolicy=4 — stops most PowerShell attack scripts
3. ASR Rules: Enabled "Block credential stealing from LSASS" in Defender

Re-ran Atomic T1003.001 number 2. Access Denied. The attack now fails AND the Sigma rule still alerts on the attempt. Defense-in-depth achieved.
